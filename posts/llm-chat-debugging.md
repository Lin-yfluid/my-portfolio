# 大模型对话系统联调：429 限流与不听话的模型

做 AI 对话综合系统时，前端写完、接口通了的那个瞬间我以为要收工了，结果真正的麻烦才刚开始。这篇把联调阶段最耗时的几个问题记录下来。

## 一、问题一：429 请求限流

**现象**：调试高峰期频繁返回 429，页面直接抛出原始错误，用户体验很差。

**原因**：我每次改代码都会连续发多条测试请求，很容易触发服务端频率限制。

**解决思路**：

```python
# 简化版：节流 + 指数退避重试
def request_with_retry(payload, max_retry=3):
    for attempt in range(max_retry):
        resp = call_api(payload)
        if resp.status_code == 429:
            wait = 2 ** attempt          # 1s, 2s, 4s
            time.sleep(wait)
            continue
        return resp
    raise ApiError("请求过于频繁，请稍后再试")
```

同时把错误统一封装成**用户可以看懂的提示**，而不是把 `429 Too Many Requests` 原样弹出来。

**经验**：开发阶段就该准备好限流处理，不能等上线才发现。

## 二、问题二：模型不遵循指令

**现象**：System Prompt 里写清了"只用一句话回答"，模型依然给三段。

**排查过程**：

1. 先确认 Prompt 真的传过去了（打印完整请求体）——发现拼接时把 system 消息位置放错了
2. 修正后仍有偏差，于是调整 Prompt 结构：角色 → 约束 → 示例
3. 配合 temperature 调低，输出稳定性明显提升

最终形成的 Prompt 模板：

```text
【角色】你是……，说话风格是……
【约束】回答不超过一句话；不确定时明确说不确定
【示例】用户：xxx → 你：yyy
```

三个部分缺一个效果就掉档。尤其**示例**，模型对示例的模仿远比对抽象描述敏感。

## 三、问题三：上下文断裂

**现象**：聊到第 5、6 轮后模型"失忆"，或者把前面的话重复一遍。

**原因**：历史消息无限拼接，超出上下文窗口后被截断，而截断把最关键的 System Prompt 也挤掉了。

**解决**：固定 System Prompt 在最前，尾部保留最近 N 轮，中间的旧消息按摘要方式压缩。这需要前端和后端一起约定消息结构。

## 四、问题四：前后端传参不一致

这个最隐蔽。前端传的字段名是 `messages`，后端读的是 `history`，接口不报错，只是模型永远只看到最后一句话。

**排查方法**：把两端的 payload 都打印出来对比。这类问题一次排查完，后面加个约定文档就不会再犯。

## 五、我的联调检查清单

```
□ System Prompt 是否在正确位置
□ 历史消息截断策略是否会挤掉关键约束
□ 429 / 5xx 是否有重试与友好提示
□ 前后端字段名是否一致
□ 多轮对话是否真的维持住了人设
□ 异常是否被统一封装而非原样抛出
```

## 六、复盘

联调阶段真正花时间的不是写功能，而是"确认数据到底传成了什么样"。我的结论是：**多在链路上打日志，比猜原因高效十倍**。所有"莫名其妙"的问题，最后都能在某个具体的请求体或响应体里找到答案。
